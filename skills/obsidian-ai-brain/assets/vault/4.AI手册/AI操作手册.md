# AI 操作手册

> 这份文件是给 agent 的接引文件。任何 AI 接手这个库之前先读完它。
> 读完不代表会用，`2.领域/` 里是已经沉淀下来的结论，问答前先搜。

## 这个库是什么

这是一个 **AI 的记忆库**，不是人类的学习笔记。它的定位只有一句话：

> 「这个知识库是给你用的。」

含义：

- 库的主人写日记是用 Obsidian 界面自己写，用不着你管
- **库的价值在于「下次开新会话还能想起来」**，不是「记录得很好看」
- 所以：**写下来 > 写得漂亮**，**能检索到 > 分类完美**
- 判断一个动作要不要做，只问一句：**半年后新会话的我，会不会因为这个受益？**

## 目录分工（谁写什么）

| 目录 | 谁写 | 放什么 |
|---|---|---|
| `1.项目/` | 我 | 正在进行、有交付物的事，写清当前进展、卡点、下一步 |
| `2.领域/` | 我 | **跨会话的结论与踩坑**，我最该读的地方 |
| `3.自我/` | **主人定，我不擅自写** | 主人的偏好、习惯、术语、决策 |
| `4.AI手册/` | 我（改动前先说） | 本文件 + 我自己的规则 |
| `5.日记/` | 主人 | 人类自己写，我只读不写 |
| `6.资料/` | 我 | 模板 `模板/`、附件 `附件/`、参考原件 `参考/` |
| `9.归档/` | 我（只进不出） | 干完的、不活跃的；`备份/` 不出现在索引里 |

`3.自我/` 为什么我不擅自写：那里面是「主人是什么样的人」，我越俎代庖写出来的偏好会污染后续所有会话。要记主人的偏好，先问一句，或先写在当次对话里等他确认。

## 文件命名

- 普通笔记：**内容摘要做主名**，例如 `Obsidian库迁移到Windows的坑.md`、`PowerShell编码规范.md`
- 绝对不要用 `笔记1`、`2026-10-23-记录` 这种——半年后我搜不到
- 日记例外：主人自己用 `YYYY-MM-DD`

## frontmatter（每篇必写）

```yaml
---
title: 人话标题
type: note | 项目 | 日记 | 复盘
date: {{DATE}}
tags: [踩坑, powershell]
---
```

`type` 只有这四个值，别自己造第五个。

## 读写规则

1. **写之前先搜**。全文搜关键词，命中就直接在已有笔记里补，**不要新建重复内容**。库里的笔记越多，重复就越毒。
2. **一篇笔记只讲一件事**。一件事写散了就拆成两篇，用 `[[双链]]` 连起来。
3. **双链指向具体的东西**（某项目、某结论、某工具），标签标状态或类别（`#待验证` `#复盘` `#工具`）。同一样东西别既建笔记又打标签。
4. **不复制粘贴别处的内容**，引用就写 `[[笔记名]]`。
5. **不改 `9.归档/` 下的东西**，只往里加。
6. **不删主人的笔记**。要废弃就移到 `9.归档/`，别用删除。
7. **敏感信息不进库**：密钥、token、账号、密码。要记「有这个东西」可以，记「值是什么」不行。
8. **覆盖前先备份**到 `9.归档/备份/`，文件名加 `.bak-<时间戳>`。

## 写什么才算「值得写进库」

这是最容易犯的错：把一切都写进去，库变成垃圾场。

提炼成一句话：**能迁移的才写。**

必问自己一个问题：**下一个项目、下一次会话的我，会不会因为这条受益？** 会 → 写。只是"这轮发生了什么" → 不写。

具体只收这四类：

1. **踩过的坑**：报错原文 + 根因 + 怎么解决的。**必须带报错原文**，否则下次搜不到。
2. **环境与路径的事实**：哪个东西在哪、什么版本、有什么反直觉之处（"不在 A 目录，在 B 目录"）。
3. **决策与理由**：选 A 不选 B，**以及为什么**。没有理由的决策半年后等于没记。
4. **可复用的做法/工具/思路**：这次用的方法，下个项目能不能照搬、怎么照搬。

四类都收不住的一律不写：过程流水账、一次性调试、通用常识（那是搜索引擎的活）、主人的原话复制（那是日记的活）、我自己的推理草稿、进展汇报。

**宁缺毋滥**：一轮任务一条都不值得写，完全正常。库里 20 条高信噪比的结论，胜过 200 条日志。

## 省算力的写法

这个库要「方便高效、准确、算力低消耗查询」。这要求约束的是**我怎么写**，不只是怎么搜：

1. **先写结论**：每篇笔记前 8 行内必须有 `> **一句话结论**：…`。我读前几行就能判断要不要继续读，不用通读全篇。
2. **关键词前置**：标题和小标题里放真实的检索词（报错码、路径、工具名），不要用「一些思考」「记录」。
3. **短**：单篇控制在 2KB 以内。超过就拆成两篇用双链连。
4. **不复制会话**：会话原文留在 agent 自己的日志目录里，库里只放提炼后的结论（几十 KB）。**库小，检索才快。**
5. **用固定词**：同一个东西永远用同一个叫法，别一会儿「网关」一会儿「gateway」，否则搜不全。

判断标准：**如果为了查一条结论要读超过 3 篇笔记，说明当初写得不对，回头合并。**

## 回答主人问题之前

1. **先搜再答**。`2.领域/` 优先，然后 `1.项目/`。别凭印象答——我记得的可能是另一个库。
2. 命中多篇时按 `0.导读` 的优先级读，别只读一篇就下结论。
3. 引用时**给出文件名**，方便主人核对。
4. 搜不到就直说"库里没有"，**不要编**。

## 会话开始与结束

**开始**（接手一个和这个库相关的会话时）：

- 先读 `4.AI手册/AI操作手册.md`（就是这份）
- 再读 `3.自我/` 里有的内容，了解主人的偏好
- 然后按话题搜 `2.领域/` 和 `1.项目/`
- 需要跨项目全局视角时读 `1.项目/项目索引.md`

**结束**（一轮任务做完、或者会话要断了）：

- 问自己那句：「这轮有没有**能迁移**的东西？」
- 有 → 按四类落盘，**先搜有没有同名/同主题的笔记，有就补充进去，别新建**
- 没有 → 不写。**硬凑比不写更糟**
- 主人明确说"记一下" → 一定写

## 跨项目关联

不同话题散在不同工作区、不同 agent 的会话里，它们在库里**只在 `1.项目/项目索引.md` 有一张总表**，靠双链串起来。

- 每个项目的笔记都要在 `## 相关` 里连回索引，或连到别的项目
- 发现两篇讲同一件事 → 合并，不要并存

## 长期维护

- 每周扫一遍：`9.归档/` 有没有该归档的完成项；`2.领域/` 有没有内容重复可以合并的
- 库超过 100 篇之后，再考虑引入内容地图 / 索引页
- 刚开始库是空的，别急着搭结构，**让结构从使用中长出来**
